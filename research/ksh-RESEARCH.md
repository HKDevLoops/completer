Status: **INSPECTION-ONLY**. `ksh`, `ksh93` and `mksh` are absent on this host
(verified with `Get-Command tcsh,csh,ksh,ksh93,mksh -ErrorAction SilentlyContinue`,

shell, `github.com/MirBSD/mksh`, pdksh-derived).

## Config / RC path(s)

### ksh93
The ksh93 man page documents the `ENV` variable, verbatim:

> "ENV — If this variable is set, then parameter expansion, command substitution,
> and arithmetic substitution are performed on the value to generate the pathname
> of the script that will be executed when the shell is invoked interactively
> (see Invocation below). This file is typically used for alias and function
> definitions. The default value is `$HOME/.kshrc`. On systems that support a
> system wide `/etc/ksh.kshrc` initialization file, if the filename generated by
> the expansion of ENV begins with `/.` or `./`, the system wide initialization
> file will not be executed."

Source: https://linux.die.net/man/1/ksh93 (Shell Variables, `ENV`);
https://raw.githubusercontent.com/ksh93/ksh/master/src/cmd/ksh93/sh.1 (line ~2150–2167)

Login shells read the standard profiles. The OpenBSD ksh man page (pdksh family)
states verbatim:

> "-l — Login shell. If the basename the shell is called with (i.e. argv[0])
> starts with '-' or if this option is used, the shell is assumed to be a login
> shell and the shell reads and executes the contents of /etc/profile and
> $HOME/.profile if they exist and are readable."

Source: https://man.openbsd.org/ksh.1 (DESCRIPTION, `-l`)

### mksh
The official mksh man page `FILES` section lists verbatim:

```
~/.mkshrc        User mkshrc profile (non-privileged interactive shells)
~/.profile       User profile (non-privileged login shells)
/etc/profile     System profile (login shells)
/etc/shells      Shell database
/etc/suid_profile Privileged shells' profile (sugid)
```

> "The location can be changed at compile time (e.g. for embedded systems); AOSP
> Android builds use /system/etc/mkshrc."

Source: https://raw.githubusercontent.com/MirBSD/mksh/master/mksh.1 (FILES, line ~7196–7215)

The mksh "Startup files" section states:

> "Non-privileged interactive shells perform parameter, command, arithmetic and
> tilde (~) substitution on the ENV parameter next; if the result is unset or
> empty, the user mkshrc profile is processed."

Source: https://raw.githubusercontent.com/MirBSD/mksh/master/mksh.1 (Startup files)

### Windows
No Windows-specific rc path for ksh93 or mksh is documented in any of the
fetched official sources. The carapace setup page has no ksh/mksh section at all.
Source: https://carapace-sh.github.io/carapace-bin/setup.html

## Native completion API

### ksh93 — built-in editor completion + KEYBD trap (no `complete` builtin)

The ksh93 man page describes built-in completion/listing as editor operations,
verbatim:

> "Each of the edit modes has an operation to list the files or commands that
> match a partially entered word. When applied to the first word on the line, or
> the first word after a ;, |, &, or (, and the word does not begin with ~ or
> contain a /, the list of aliases, functions, and executable commands defined
> by the PATH variable that could match the partial word is displayed. Otherwise,
> the list of files that match the given word is displayed. ... There are
> additional operations, referred to as command name completion and file name
> completion, which compute the list of matching commands or files, but instead
> of printing the list, replace the current word with a complete or partial
> match. ... When using a tab for completion that does not yield a unique match,
> a subsequent tab will provide a numbered list of matching alternatives. A
> specific selection can be made by entering the selection number followed by a
> tab."

Source: https://linux.die.net/man/1/ksh93 (In-line Editing Options);
https://raw.githubusercontent.com/ksh93/ksh/master/src/cmd/ksh93/sh.1 (line ~5251–5294)

For programmable completion, ksh93 documents the `KEYBD` trap and its special
variables — the official mechanism for intercepting keystrokes and injecting
text, verbatim:

> "The KEYBD trap can be used to intercept keys as they are typed and change the
> characters that are actually seen by the shell. This trap is executed after
> each character (or sequence of characters when the first character is ESC) is
> entered while reading from a terminal. The variable .sh.edchar contains the
> character or character sequence which generated the trap. Changing the value
> of .sh.edchar in the trap action causes the shell to behave as if the new value
> were entered from the keyboard rather than the original value."
>
> "The variable .sh.edcol is set to the input column number of the cursor at the
> time of the input. The variable .sh.edmode is set to ESC when in vi input mode
> and set to the empty string otherwise. Prepending ${.sh.edmode} to a value
> assigned to .sh.edchar will cause the shell to change to control mode if it is
> not already in this mode."
>
> ".sh.edtext — The characters in the input buffer at the time of the most recent
> KEYBD trap. The variable is unset when not processing a KEYBD trap."

Source: https://raw.githubusercontent.com/ksh93/ksh/master/src/cmd/ksh93/sh.1
(Key Bindings, line ~5295–5335; Shell Variables `.sh.edchar`, `.sh.edcol`,
`.sh.edmode`, `.sh.edtext`, line ~1807–1850);
https://linux.die.net/man/1/ksh93 (Key Bindings)

Shape of the documented mechanism (derived from the documented variables; the
man page describes the trap and variables but does not provide a turnkey
completion function):

```
trap '...inspect .sh.edtext / .sh.edcol; assign .sh.edchar...' KEYBD
```

### mksh — `complete_*` arrays (pdksh-family) and editor `complete`

The OpenBSD ksh man page (pdksh family, same completion mechanism) documents
custom per-command completions verbatim:

> "Custom completions may be configured by creating an array named
> 'complete_command', optionally suffixed with an argument number to complete
> only for a single argument. So defining an array named 'complete_kill' provides
> possible completions for any argument to the kill(1) command, but
> 'complete_kill_1' only completes the first argument. For example, the following
> command makes ksh offer a selection of signal names for the first argument to
> kill(1):"

```
set -A complete_kill_1 -- -9 -HUP -INFO -KILL -TERM
```

Source: https://man.openbsd.org/ksh.1 (Editor commands, `complete: ^[^[`)

**Attribution caveat:** mksh's own official man page (GitHub raw `mksh.1`) documents
the editor `complete` command but does **not** document the `complete_*` array
mechanism (a search of that manual for `complete_` returned no matches). The array
mechanism above is documented by the OpenBSD ksh (pdksh-family) man page only.

The mksh man page documents the editor completion commands verbatim:

```
complete: ^[^[
```

> "Automatically completes as much as is unique of the command name or the file
> name containing the cursor. If the entire remaining command or file name is
> unique, a space is printed after its completion, unless it is a directory name
> in which case '/' is appended. If there is no command or file name with the
> current partial word as its prefix, a bell character is output."

```
complete-list: ^I, ^[=
```

> "Complete as much as is possible of the current word and list the possible
> completions for it. If only one completion is possible, match as in the complete
> command above. Note that ^I is usually generated by the Tab (tabulator) key."

Source: https://raw.githubusercontent.com/MirBSD/mksh/master/mksh.1
(Editor commands, line ~6274–6302)

mksh also exposes completion-related options (`vi-esccomplete`, `vi-tabcomplete`)
documented as:

> "In vi command-line editing, do command and file name completion when Esc/Tab
> is pressed."

Source: https://raw.githubusercontent.com/MirBSD/mksh/master/mksh.1 (line ~4843–4847)

## Alias add / remove (native mechanism)

### ksh93
The ksh93 man page states verbatim:

> "Aliases can be created and listed with the alias command and can be removed
> with the unalias command."
>
> "Aliasing is performed when scripts are read, not while they are executed.
> Therefore, for an alias to take effect, the alias definition command has to be
> executed before the command which references the alias is read."

Source: https://linux.die.net/man/1/ksh93 (Aliasing)

The builtin syntax from the project-hosted manual:

```
alias [ -ptx ] [ name[=value] ... ]
```

> "alias with no arguments prints the list of aliases"

Source: https://raw.githubusercontent.com/ksh93/ksh/master/src/cmd/ksh93/sh.1
(line ~6544–6546); `unalias` builtin at line ~9899

### mksh
The OpenBSD ksh man page states:

> "Command aliases are normally used as a short hand for a long or often used
> command. The shell expands command aliases (i.e. substitutes the alias name for
> its value) when it reads the first word of a command."
>
> "Tracked aliases can be listed and created using alias -t."

Source: https://man.openbsd.org/ksh.1 (Aliases)

Concretely (derived from the documented grammar, valid in both):

```
alias completer='path/to/completer'
unalias completer
```

## Sourcing generated files

Both shells use the POSIX dot (`.`) builtin. The ksh93 manual documents:

```
. filename
```

> "Include the assignment commands contained in filename."

Source: https://raw.githubusercontent.com/ksh93/ksh/master/src/cmd/ksh93/sh.1
(Variable Assignments)

The OpenBSD ksh man page refers to "a script sourced using the '.' built-in
command", and the ksh93 man page lists the preset alias:

```
source='command . '
```

Source: https://man.openbsd.org/ksh.1 ; https://linux.die.net/man/1/ksh93
(Aliasing, compiled-in aliases)

Concretely:

```
. /path/to/completer/completer.ksh
```

## Self-completion (completion for its OWN `completer` function)

### ksh93 — NO documented per-command registration API
The ksh93 manual documents no `complete` builtin and no per-command completion
registration API; programmable completion is only the generic `KEYBD` trap
keystroke interception described above. Generic command-name completion does
include functions automatically:

> "the list of aliases, functions, and executable commands defined by the PATH
> variable that could match the partial word is displayed"

Source: https://linux.die.net/man/1/ksh93 (In-line Editing Options)

So a function named `completer` is covered by generic command-name completion,
but there is no documented way in ksh93 to register a dedicated completion for
its arguments. No exact `ksh93` self-completion snippet can be cited from the
official docs.

### mksh (pdksh-family) — YES, via `complete_*` arrays (with attribution caveat)
Applying the documented `complete_<command>` / `complete_<command>_<argnum>`
array mechanism (documented by the OpenBSD ksh man page, not by mksh's own
manual), a completion for a command named `completer` is:

```
set -A complete_completer_1 -- add remove list update
```

And, by analogy with the documented `complete_kill` (any argument) form:

```
set -A complete_completer -- add remove list update
```

Source for mechanism + verbatim `set -A complete_kill_1 -- ...` example:
https://man.openbsd.org/ksh.1 (Editor commands, `complete: ^[^[`)

These `completer` snippets are derived from the documented grammar; no official
doc contains a literal `completer` example.
